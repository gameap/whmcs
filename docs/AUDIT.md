# Module audit and compatibility with GameAP 4.5.0

Date: 2026-09-03. Subject: `modules/servers/gameap` as of 2026-08-18 (version 1.0.0).

## How it was verified

- **API reference** — the panel sources at `github.com/gameap/gameap`, tag
  `v4.5.0` (commit `6f8f727`): the router (`internal/api/router.go`), the
  handlers, `internal/domain`, `pkg/api`, OpenAPI.
- **WHMCS** — the official developers.whmcs.com documentation (module
  parameters, service properties, UpdateClientProduct, single sign-on, hooks,
  meta data, whmcs.json), the sample-provisioning-module and client theme
  sources, and, for undocumented behaviour, the WHMCS 8.13 core code.
- **Live panel** — `gameap/gameap:4.5.0` in docker (SQLite, a dummy node with
  no daemon). Every request/response shape below marked "live" was checked
  with curl, and then the whole module was run against the panel end-to-end:
  Test Connection → create → second create → suspend → reconcile → unsuspend →
  changePackage → status → reconcile → terminate.

None of the endpoints the module needs existed in 4.4.x in a token-accessible
form: the `admin:user:*`, `admin:node:read`, `admin:game:read`,
`admin:user:sso` abilities and SSO tickets appeared in 4.5.0. The 4.5.0
minimum version is correct.

## Confirmed against a live 4.5.0 panel

| Check                                                                        | Result                                                                   |
| ---------------------------------------------------------------------------- | ------------------------------------------------------------------------ |
| `POST /api/servers` with body `[]` / `{}`                                    | 500 / 422 `name is required`                                             |
| `POST /api/users`, `POST /api/auth/sso/tickets` with `{}`                    | 400 `login is required` / 422 `user_id is required`                      |
| `POST /api/servers`, valid                                                   | 201 `{"message":"success","result":{"taskId":0,"serverId":1}}`           |
| `GET /api/servers/{id}` after setting `metadata.public_ip`                   | `server_ip` = the published one, `internal_server_ip` = the real one     |
| `PUT /api/servers/{id}` with `blocked`, `cpu_limit`, `ram_limit`, `metadata` | 200 `{"status":"ok"}`, values persisted                                  |
| `PUT /api/users/{id}/servers/{server}` twice                                 | 204, 204 (idempotent)                                                    |
| `PUT …/permissions` with the 14 permissions including `game-server-pause`    | 200                                                                      |
| `PUT …/settings` with an unknown name                                        | 200, the name silently skipped                                           |
| `POST …/stop`, then `DELETE` with no body                                    | 409 `server has pending tasks`                                           |
| `DELETE` with `{"delete_files":true}`, then `GET`                            | 204, 404                                                                 |
| `PUT /api/users/{id}` with `password` from a PAT                             | 403 `personal access tokens cannot change passwords`                     |
| `POST /api/auth/sso/tickets`                                                 | `{"ticket":"glsso_…","expires_in":60,"redirect_to":"/servers/1"}`        |
| `GET /api/users?filter[email]=…`                                             | a bare array, case-insensitive                                           |
| `GET /api/nodes`, `…/ip_list`, `…/busy_ports`                                | `ip` is an array; an array of strings; a map of ip → [all three ports]   |
| `GET /api/games/{code}/mods` for an unknown code                             | 200 `[]`                                                                 |
| Module end-to-end (create → … → terminate)                                   | every step succeeds; a second `create()` does not create a second server |

## Known limitations

- The panel does not check ip:port uniqueness. The module scans busy ports
  before creating; two servers created simultaneously on the same port would
  both be accepted by the panel.
- If server creation finished on the panel side but the response never reached
  the module (30 s timeout), a retry creates a second server: the panel offers
  no way to find a server by name or metadata before the module has learned
  its id.
- Test Connection cannot verify the `server:start/stop/restart/settings-manage`
  abilities: they require an existing server.
